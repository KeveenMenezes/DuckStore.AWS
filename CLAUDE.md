# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

DuckStore is a **serverless-first AWS** .NET microservices e-commerce sample, orchestrated locally by .NET Aspire. It uses Vertical Slice Architecture, CQRS (MediatR), AWS Lambda functions, DynamoDB, and Amazon EventBridge. It's a learning/demo project, not production software — favor consistency with existing patterns over introducing new ones.

The codebase is mid-evolution: it was migrated from a classic stack (PostgreSQL/Marten, EF Core, RabbitMQ/MassTransit, gRPC, Carter) to serverless AWS. Architectural decisions are recorded under `docs/adr/` (49+ ADRs, numbered sequentially) — **read the relevant ADR before changing cross-cutting infrastructure**. Foundational ones: ADR-0004 (EventBridge over MassTransit/RabbitMQ), ADR-0005 (removal of in-process domain events; CDC via DynamoDB Streams), ADR-0006 (React/Next.js as the primary SPA), ADR-0019 (module-oriented service structure + rule-based stream publishers — the pattern every service below follows). Most recent Accepted: ADR-0052 (Inventory bounded context: warehouses owned by the StockKeeper group; §7 stock balances and the immutable movements ledger), ADR-0048 (points ledger and in-cart redemption) and ADR-0049 (purchase-gated review lifecycle: Eligible/Published/Deleted); ADR-0050 (checkout as a Step Functions Express saga) is Proposed and implemented on the `feat/checkout-sagas` branch; ADR-0046 (Challenge points redeemed into a customer-scoped Pricing discount) is the redemption baseline ADR-0048 amends; ADR-0040 established the strategy-dispatch grouping pattern CatalogView follows. Use the `adr` skill to author/update ADRs.

Target framework is **net10.0** across all .NET projects.

## Common commands

```bash
# Build the whole solution
dotnet build DuckStore.slnx

# Run everything (Aspire orchestrates Lambda functions, DynamoDB Local, the Lambda emulator,
# Elasticsearch/Kibana, and the web apps)
dotnet run --project src/AppHost/AppHost.csproj

# Run all .NET tests
dotnet test

# Run a single test project
dotnet test tests/Services/Catalog/Catalog.UnitTests/Catalog.UnitTests.csproj

# Run a single test by name
dotnet test --filter "FullyQualifiedName~CheckoutBasketCommandHandlerTests"

# End-to-end tests against a deployed environment (skipped unless E2E_* is set — see tests/E2E/README.md)
dotnet test tests/E2E/Checkout/Checkout.E2ETests
dotnet test tests/E2E/Inventory/Inventory.E2ETests   # management app; staff users in ~/.config/duckstore/e2e-inventory.env

# Format code (also runs automatically on staged .cs files via .githooks/pre-commit)
dotnet format DuckStore.slnx

# Validate infra/ (CDK) changes locally before pushing — CI runs `cdk deploy` per service on merge
cd infra && npx cdk synth <StackName>   # e.g. OrderingStack
cd infra && npx cdk diff <StackName>
```

Git hooks live in `.githooks/` (configured via `core.hooksPath`); the pre-commit hook runs `dotnet format` on staged `.cs` files and re-stages them. Don't bypass this with `--no-verify`.

Use `dotnet run --project src/AppHost/AppHost.csproj` (Aspire) to start the system locally — it provisions DynamoDB Local (`http://localhost:8000`), the Aspire AWS Lambda service emulator, and Elasticsearch/Kibana as containers, registers each Lambda function, and wires the dev environment between them. Aspire is the only local orchestration path — there is no docker-compose fallback.

The Go notification service and the React SPA have their own toolchains (`go`, `pnpm`/`next`) — see those subsections.

## Architecture

### The serverless model

- **Compute** is AWS Lambda. Each use case is its own function. Locally, Aspire registers them via `AddAWSLambdaFunction<Projects.X>(...)` and runs them through the Lambda service emulator.
- **Persistence** is DynamoDB (DynamoDB Local in dev). Repositories talk to `IAmazonDynamoDB` directly (`TransactWriteItems`, etc.) — there is no EF Core `SaveChanges`/`ChangeTracker`/interceptor pipeline anymore.
- **Cross-service messaging** is Amazon EventBridge (`BuildingBlocks.Messaging/EventBridge`). The bus only exists on AWS; locally, publishes are **best-effort and fail silently**. Integration events are produced via **Change Data Capture**: a committed DynamoDB write → DynamoDB Streams → a Stream-triggered publisher Lambda → EventBridge (see ADR-0005). Do not reintroduce in-process domain events as the integration path. Lambda function names follow `<service>-<resource>-stream-publisher` for CDC-out publishers and `<service>-<resource>-sync-consumer`/`-consumer` for CDC-in consumers — keep new functions consistent with this.
- **Synchronous service-to-service calls** use direct Lambda invocation via the AWS Lambda Invoke API, not gRPC/HTTP (e.g. Payment → PaymentGateway). The former Basket → Discount invoke was removed by ADR-0012, which folded `Coupon` into Basket as an in-process entity; ADR-0026 later superseded that and moved discount/campaign ownership out of Basket entirely into Pricing — Basket now has zero discount responsibility and never calls Pricing, sync or async.

### Lambda function pattern (all services)

Each `*.Function` project uses the **Amazon.Lambda.Annotations** source generator:

- A `partial class Functions` holds methods decorated with `[LambdaFunction]` + `[HttpApi(...)]` (or other event-source attributes). The generator emits the actual handler types referenced in the AppHost as `X.Function::X.Function.Functions_<Method>_Generated::<Method>`. When you add/rename a function method, the AppHost `lambdaHandler` string must match the generated name.
- DI is configured in a `[LambdaStartup] public class Startup.ConfigureServices(IServiceCollection)`. Configuration comes from environment variables that Aspire injects (`ConnectionStrings__*`, `services__*`, `EventBridge__*`, AWS dev credentials/region).
- Endpoints map the HTTP request to a MediatR command/query via `ISender.Send(...)` and adapt request/response DTOs (Mapster `.Adapt<T>()`, convention-based).
- Every `*.Function` project (except `User.Function`, which stays a plain class library) deploys as a self-contained **Native AOT ZIP on `provided.al2023`** (arm64), not a container image (ADR-0042).

### CQRS conventions (all .NET services)

- Commands implement `ICommand<TResponse>`, queries implement `IQuery<TResponse>` (from `BuildingBlocks.Core`), handled by `ICommandHandler<,>`/`IQueryHandler<,>` over MediatR.
- The MediatR pipeline in Lambda startups registers `ValidationBehavior` (FluentValidation `AbstractValidator<TCommand>`) and `LoggingBehavior` from `BuildingBlocks.ServiceDefaults.Behaviors`. (The old `UnitOfWorkBehavior` is gone — there is no DB transaction scope to manage.)
- Slices live under `Features/{UseCase}/` (e.g. `Features/Products/CreateProduct`, `Features/CheckoutBasket`), each holding endpoint + command/query + handler + validator together.

### Services (src/Services/*)

- **Basket.Function** — Lambda + DynamoDB (`IShoppingCartRepository`/`DynamoShoppingCartRepository`, no caching layer — ADR-0013; DI wired in `ServiceRegistration.AddBasketServices`). `ShoppingCart` is the aggregate root (`Aggregate<OwnerId>`); identity is a server-resolved, prefixed `OwnerId` — `USER#<cognito-sub>` for authenticated carts or `GUEST#<guestId>` for visitor carts, the latter TTL-expirable in DynamoDB (ADR-0016). Basket has **zero discount responsibility**: `Coupon`/`DynamoCouponRepository`/the `coupons` table were removed and discount/campaign ownership moved to Pricing (ADR-0026, supersedes ADR-0012 §1/§2). Checkout publishes to EventBridge (CDC). Slices under `Features/{StoreBasket,CheckoutBasket}`. `checkoutBasket` runs the **`checkout-saga`** Step Functions Express state machine (ADR-0050, replacing the ADR-0048 §4 pipeline): `OrderId` derived from `(ownerId, checkoutId)` → replay check (`CHECKOUT#<owner>#<checkoutId>` record) → saved cart (`ProductId`/`Quantity`/`Version` only) → Catalog names/images → Pricing quote (total charged + per-line prices, or `PriceChanged`/`PointsAboveCap`) → `payment-register` → `basket-checkout-basket`, which closes the cart in one `TransactWriteItems` (Put the `CHECKOUT#` record + Delete the cart only if its `Version` is the one quoted, else `CartChanged`) → `payment-void` only on `CartChanged`. Refusals end the execution `SUCCEEDED` with a `refusal` payload; only real faults end `FAILED` (alarmed). `basket-checkout-basket` has no Function URL and is invoked only by the saga. `CheckoutedRule` publishes on the `CHECKOUT#` INSERT. Basket passes `PointsToUse` through without interpreting it and never sees the card.
- **Catalog.Function** — Lambda + DynamoDB (`DynamoProductRepository`, `DynamoCategoryRepository`). Slices under `Features/Products/*` and `Features/Categories/*`.
- **Ordering.Function** — module-oriented like the rest of the reference architecture (`Modules/Orders/`), collapsed from the old `Ordering.{Domain,Application,Infrastructure}` DDD layering. Still keeps DDD types internally (`Order` aggregate + value objects, MediatR slices under `Features/`), but persistence is **DynamoDB** (`ordering`) via `DynamoOrderRepository`. Each order is a **single item** with its `OrderItems` embedded as a list attribute — written with one `PutItem` (atomic on its own; no `TransactWriteItems`), read by `Id` with `GetItem`, listed by customer through GSI1 (`ProjectionType.ALL`, no N+1). `Aggregate<TId>`/`IAggregate` are empty aggregate-root markers (domain events removed — ADR-0005). CDC Lambdas live under `Modules/Orders/EventsIntegration/`:
  - `Consumers/BasketCheckout/` — consumes the checkout integration event and writes the order (idempotent via the `ordering-processed-events` inbox).
  - `Consumers/PaymentResult/` — two `[LambdaFunction]` entry points (`OrderPaymentAuthorizedConsumer`/`OrderPaymentDeclinedConsumer`, one EventBridge rule each) both delegating to the same handler, which applies the Payment service's result to transition the order `Pending → Completed`/`Cancelled`.
  - `Publishers/OrderStreamPublisherFunction` — DynamoDB Streams source on `ordering`; publishes `OrderCreated`, `OrderCompleted` on the `Pending → Completed` transition (consumed by Review, ADR-0049) and `OrderCancelled` on any transition into `Cancelled` (consumed by Challenges to give reserved points back, ADR-0048 §5), to EventBridge (CDC).
  - `Ordering.DevelopmentDataSeeder` — separate Worker that creates/seeds DynamoDB tables (`DynamoTableInitializer`, in the Function project) before the Ordering Lambdas start.
- **CatalogView.Function** — read-model/search bounded context fed by CDC from Catalog, Review, Pricing and Inventory (ADR-0027/ADR-0030, DynamoDB-backed). Inbound consumers are grouped **by producer bounded context**, not by individual event (ADR-0040): `Modules/Products/EventsIntegration/Consumers/CatalogSync/` (dispatcher + `ICatalogSyncStrategy` strategies for `ProductSynced`/`ProductDeleted`/`CatalogCategorySync`) and `Consumers/ReviewSync/` (dispatcher + `IReviewSyncStrategy` strategies for `ReviewCreated`/`ReviewUpdated`/`ReviewDeleted`). `Consumers/PricingSync/` (dispatcher + `IPricingSyncStrategy`, ADR-0044) handles Pricing's CDC events (`PriceChangedEvent`, `ProductDiscountChangedEvent`). `Consumers/InventorySync/` is a plain 1:1 handler for Inventory's single event, `ProductStockChangedEvent` (ADR-0052 §8). It writes `Stock` only when the event's `Version` is greater than the stored `StockVersion`, and it upserts, so a total that arrives before `ProductSynced` waits on a stock-only item. An item without a `Name` is not a product: `product`/`products` skip it. Each producer gets its own strategy interface; never share one across producers or fall back to an in-handler `switch`.
- **Payment.Function** — simulates payment authorization for orders (ADR-0025). The checkout saga registers the payment through `payment-register` (card validated — Luhn, expiry, CVV — status `Registered`, `PaymentId = OrderId`; `InvalidCard`/`CheckoutRetryRequired` refusals) and voids it through `payment-void` on `CartChanged` (ADR-0050 §6). `payment-basket-checkout-consumer` then promotes it off `BasketCheckoutEvent` (`Registered` or `Voided` → `Pending`; it throws when no payment was registered). The gateway round trip is event-driven: `PaymentRequestedEvent` → `PaymentGateway.Function` → `PaymentAuthorizedEvent`/`PaymentDeclinedEvent`. A checkout that used points promotes the payment to `AwaitingPoints` instead of `Pending` (ADR-0048 §6): `payment-points-reserved-consumer` moves it on to `Pending` (and so to the gateway), `payment-points-reservation-failed-consumer` declines it with `InsufficientPoints`, and `PaymentDeclinedInsufficientPointsRule` publishes that decline so Ordering cancels the order. DynamoDB: `payments` + `payment-processed-events` (idempotency inbox).
- **PaymentGateway.Function** — the simulated external payment processor (`Modules/Gateway`), invoked synchronously by Payment; decides authorize/decline outcomes.
- **Pricing.Function** — owns product pricing and promotional campaigns (ADR-0026). `Campaigns` module (`CreateCampaign`/`EndCampaign` features, plus the `CartDiscountAllocation` domain service that allocates a per-product campaign discount proportionally against the cart's single billed price — ADR-0043), `Prices` module (consumes `ProductDeleted` for cleanup, publishes price changes via CDC, `GetInstallmentPlan`/`GetBasketInstallmentPlan` queries; `pricing-product-discounts-stream-publisher` publishes `ProductDiscountChangedEvent` off the `product-discounts` stream so a campaign write — which never touches `prices` — still reaches CatalogView, ADR-0044), `GatewayCosts` module (payment gateway cost tracking, ADR-0028). Points are a cart-level discount priced in `GetBasketInstallmentPlan` (ADR-0048 §3): 100 points = R$1, capped at 20% of the post-campaign price (`RewardOptions`, `Rewards__*` env vars from `infra/constructs/reward-config.ts`), applied after the campaign allocation, and a request above the cap is rejected (`PointsAboveCap`), never trimmed. The same query is the `Quote` step of the `checkout-saga`, where it also confirms the total charged (`PriceChanged`) and returns `Lines` — the per-unit, pre-points price of each cart line (`CartDiscountAllocation.LineValuesFrom`) that the order records. Every refusal (including `BadRequest` and `ProductUnavailable`) comes back as a `Rejection`, never as a Lambda error. Pricing never sees the balance; Challenges never sees money. The old coupon model (`CustomerDiscounts`, ADR-0046) was removed. DynamoDB: `prices`, `campaigns`, `product-discounts`, `gateway-costs`, `pricing-processed-events`.
- **Review.Function** — product review/rating bounded context (ADR-0011/ADR-0029, one row per composite key `ProductId#UserId` with rating delta). Reviews are purchase-gated (ADR-0049): each row has a `Status` — `Eligible` (created by `review-order-completed-consumer` off `OrderCompletedEvent`, under `Modules/Reviews/EventsIntegration/Consumers/`), `Published` (`createReview` only updates an existing row, so non-buyers can't review; rows without `Status` predate ADR-0049 and count as Published) or `Deleted` (`deleteReview`, removed by TTL on `ExpiresAt` 5 days later). Only Published rows carry the sparse GSI1 keys `reviewsByProduct` reads. `Modules/Reviews/EventsIntegration/Publishers/` publishes `ReviewCreated`/`ReviewUpdated`/`ReviewDeleted` from the DynamoDB stream, keyed on the Status transition.
- **Challenges.Function** — server-side code-challenge grading and progress bounded context (ADR-0045). `Questions` module owns the question bank and answer key (`challenges` table, PK `QuestionId`/SK `PUBLIC`|`ANSWER`, sparse GSI1 so the `ANSWER` item is structurally unreachable via the public read path); `Progress` module owns per-player attempts and score (`challenge-progress`, PK `OwnerId`/SK `PROFILE`|`ATTEMPT#`, streams enabled) plus the points ledger (`points-transactions`, PK `OwnerId`/SK deterministic `TransactionId` — `CHALLENGE#`, `REVIEW#<productId>`, `REDEMPTION#<orderId>` — LSI1 by `CreatedAt` for `myPointsHistory`, sparse GSI1 by `OrderId`, streams enabled — ADR-0048): every balance change writes its ledger row in the same transaction that moves `PROFILE` `Score`, and the deterministic id is the idempotency key. `challenges-submit-answer`/`challenges-reveal-hint` are Lambda-backed AppSync mutations (ADR-0009 escalation — grading transactions/domain invariants); `updateChallengePoints` (Admin) and `myPointsHistory` are direct resolvers. Outbound CDC (ADR-0019): `challenges-progress-stream-publisher` emits `ChallengeAnsweredEvent` off `challenge-progress`; `challenges-points-transactions-stream-publisher` emits `PointsReservedEvent`/`PointsReservationFailedEvent` off `points-transactions`. Inbound consumers: `challenges-review-created-consumer` (15 points, once per product), `challenges-basket-checkout-consumer` (reserves the checkout's points: `Reserved`, or `Failed` when the balance is short), `challenges-payment-authorized-consumer` (`Reserved`→`Used`) and `challenges-order-cancelled-consumer` (`Released`/`Refunded`, points back) — the settlement consumers read the order's row by key and treat a missing row as an order without points. Challenges handles points only, never currency (ADR-0046 §1).
- **Inventory** — warehouses ("polos"), stock per product × warehouse and an immutable movements ledger (ADR-0052 §2, §7), and the only source of the storefront's stock (§8); §6 records the direction for sales. Catalog, the product inputs, the create saga and the Blazor product form have no stock. The storefront total is `Available` summed over **active** warehouses. Every balance write and every `setWarehouseActive` does `ADD Version :one`, and a total's `Version` is the sum of the counters behind it, which orders totals without a clock. `inventory-stock-stream-publisher` (balance changes) and `inventory-warehouses-stream-publisher` (an `Active` change, through the `IStreamFanOutRule` `WarehouseActivationRule`, one event per product) publish `ProductStockChangedEvent` off the two tables' streams (DLQ `inventory-dlq`). Owned by the **StockKeeper** group of the management pool (Admin can do everything it can; Seller can't, not even reads). The warehouse fields (`warehouses`/`warehouse`/`createWarehouse`/`updateWarehouse`/`setWarehouseActive`) are direct resolvers; `inventory-warehouses` (PK `WarehouseId`) holds each warehouse plus a `CODE#<code>` guard written in the same `TransactWriteItems`, which is what makes the immutable code unique — so every read filters on `Type`. Warehouses are deactivated, never deleted. Stock lives in `inventory-stock` (PK `ProductId`, SK `WarehouseId`, GSI1 by warehouse) and `inventory-movements` (PK `ProductId`, SK `MovementId`, LSI1 by date, GSI1 by warehouse); both are written only by `Inventory.Function`'s three Lambdas (`inventory-record-stock-receipt`, `inventory-record-stock-adjustment`, `inventory-transfer-stock`, rules in `StockBalance`), which answer a replay first (the `idempotencyKey` is the `MovementId`), then write balance + ledger row + warehouse `ConditionCheck` in one transaction with an optimistic condition, and return refusals as data. Receipt and adjustment are AppSync pipelines whose first step checks the product on Catalog's `products` (increases only); the four stock queries are direct, the warehouse views adding a `BatchGetItem` on `products` for names. Locally `Inventory.DevelopmentDataSeeder` creates the tables, seeds `ALPHA`/`BETA` and receives the Catalog seed products' stock into `ALPHA`. `local.ts` invokes the real Lambdas through the emulator, and since EventBridge is best-effort locally, it applies the storefront total to `catalogview-products` itself (`lib/storefront-stock.ts`). On AWS dev the storefront's stock sits in the active `DEV-VITRINE` warehouse (`scripts/inventory/seed-dev-showcase.mjs`). The Blazor app's Warehouses and Stock pages are its only client.
- **User.Function** — user profile bounded context backed by Cognito as the identity provider with lazy provisioning (ADR-0017); `DynamoUserProfileRepository` persists the profile projection.
- **ProductImages** — the only non-.NET service (`src/Services/ProductImages`, TypeScript/Node Lambdas, own `package.json`): `presign/` (presigned S3 POST for uploads), `processor/` (Sharp-based resize/optimize pipeline off an SQS queue), `scripts/sweep-orphan-images.ts` (cleanup). Dedicated S3/CloudFront bucket (ADR-0018/ADR-0034).
- **Notification** — Go service (`src/Services/Notification/Notification.Go`), consumes events and writes to DynamoDB. Has its own `go.mod` and `main_test.go` (`go test ./...`).

### BuildingBlocks (src/BuildingBlocks/*)

Shared code referenced across services — check here before adding cross-cutting concerns:

- **BuildingBlocks.Core** — `ICommand`/`IQuery`/handler interfaces, DDD base types (`Aggregate<TId>`/`IAggregate` as markers, `Entity<TId>`/`IEntity`, `ValueObject`), and shared exception types (`NotFoundException`, `BadRequestException`, `DomainException`, `InternalServerException`) surfaced as ProblemDetails by `CustomExceptionHandler`. Note: `IDomainEvent`/the domain-event machinery and `IUnitOfWork` were deleted (ADR-0005) — there's no unit-of-work or pagination abstraction; repositories query DynamoDB directly.
- **BuildingBlocks.Messaging** — `IntegrationEvent` base record and the EventBridge integration: `AddEventBridgeMessaging()` registers `IAmazonEventBridge` + `IEventPublisher` (`EventBridgePublisher`). `Streams/` holds the ADR-0019 publisher pieces: `StreamContext<TImage>`, `IStreamRule<TImage>` (one instruction per record), `IStreamFanOutRule<TImage>` (a list, for a change that publishes one event per affected entity — ADR-0052 §8) and `StreamRuleDispatcher<TImage>`, which runs both and publishes the batch in one call.
- **BuildingBlocks.ServiceDefaults** — `AddServiceDefaults()` (service discovery, Polly resilience, health checks, OpenTelemetry, Serilog → Elasticsearch), the shared MediatR `Behaviors`, and `CustomExceptionHandler` for ProblemDetails responses.
- **BuildingBlocks.ServiceDefaults.Lambda** — `AddLambdaDefaults()` (ADR-0022): the Lambda-shaped subset of ServiceDefaults — structured JSON logging to stdout/CloudWatch when running on AWS (plain console locally) and OpenTelemetry tracing of AWS SDK calls exported via OTLP when `OTEL_EXPORTER_OTLP_ENDPOINT` is set. Called by every `[LambdaStartup]` `Startup.ConfigureServices`. No Elasticsearch/health checks/service discovery (those assume a long-lived host).

### Orchestration and routing

- **src/AppHost** — .NET Aspire AppHost. `Program.cs` is the composition root; per-service wiring lives in one `*Extensions.cs` per service (`BasketExtensions`, `CatalogExtensions`, `CatalogViewExtensions`, `ChallengesExtensions`, `OrderingExtensions`, `PaymentExtensions`, `PricingExtensions`, `ReviewExtensions`, `UserExtensions`, plus `ObservabilityExtensions`). This is the source of truth for **local** infrastructure, Lambda handler names, `WaitFor`/`WaitForCompletion` chains, and DynamoDB Streams sources — for the real-AWS equivalent see `infra/` below. Shared helper in `Extensions/Extensions.cs`: `WithAwsDevEnvironment()` (dummy AWS creds + region for local dev). Add new resources/functions here — this is the only local wiring path.
- AppSync (direct DynamoDB resolvers, per ADR-0007/ADR-0009) is the only client entry point, in every environment — there is no self-hosted HTTP gateway. See ADR-0023. GraphQL schema/contract is owned at the monorepo root (ADR-0033): `graphql/schema.graphql` + resolver JS under `graphql/resolvers/<domain>/<queries|mutations>/<Type>.<field>.js`, wired into the API by `infra/constructs/appsync-api.ts` (`AppSyncStack`). Use the `resolver-selection` skill when deciding direct-DynamoDB vs. Lambda for a new field; a third kind now exists too — an HTTP data source into a Step Functions Express saga, still invoked only from behind AppSync: `createProductWithPrice` (`infra/constructs/product-create-saga.ts`, ADR-0032) writes the product and its price with compensation, and `checkoutBasket` (`infra/constructs/checkout-saga.ts`, ADR-0050) orchestrates the checkout — written as JSONata ASL so each expression can be checked with `aws stepfunctions test-state`.
- **src/WebApps/Shopping.Web.SPA.React** — React/Next.js SPA, the customer-facing storefront, fronting AppSync through its own Next.js BFF. The BFF holds Cognito tokens server-side in a `duckstore-sessions` DynamoDB table and exposes only an opaque `__Host-sid` session cookie to the browser, with `lib/auth/session.ts` as the sole module permitted to touch auth state and centralized, expiry-driven token refresh (ADR-0041, amends ADR-0016). Uses `pnpm` (`pnpm dev` / `pnpm build` / `pnpm lint`). Deployed via SST/OpenNext, not the CDK below (ADR-0020). This directory is slated to move into its own Git repository, linked back into DuckStore as a **git submodule**.
- **src/WebApps/Managment.Web.Blazor** — Blazor WebAssembly admin app (product create/edit/list, campaigns, challenge points, warehouses), calling AppSync GraphQL directly (no BFF). Menu items and pages check the Cognito group (`Auth/CognitoGroups.cs`) to hide what the resolvers would reject; the resolvers stay the authority. Deployed as a static site to S3/CloudFront. It's the client for the `createProductWithPrice` saga mutation above.

### Deployment (`infra/`)

`infra/` is a separate AWS CDK v2 TypeScript app (`infra/bin/app.ts`) — **real AWS deployment infrastructure, distinct from Aspire**. Aspire (above) only orchestrates local dev; it never touches real AWS resources. One CDK stack per service (`CatalogStack`, `BasketStack`, `OrderingStack`, `PaymentStack`, `PricingStack`, `ReviewStack`, `CatalogViewStack`, `UserStack`, `ChallengesStack`, `InventoryStack`, plus `AppSyncStack`, `ManagementStack`, `ProductImagesStack`, `MonitoringStack`, `FoundationStack`), each pairing an `infra/constructs/<service>-dynamodb.ts` (tables) with an `infra/constructs/<service>-lambdas.ts` (functions, EventBridge rules, IAM grants, DLQs). `MonitoringStack` deploys first and owns the shared `duckstore-alerts` SNS topic every DLQ alarm imports; `FoundationStack` also deploys first and owns the shared `duckstore-event-bus` EventBridge bus every service publishes to and consumes from (`RemovalPolicy.RETAIN` — a resource read by 7 stacks must not block deletion, or live inside one of its own consumers). Every stack that needs a shared resource (the bus, the alerts topic, another stack's DynamoDB table, another stack's Lambda for an AppSync data source) references it **by fixed physical name** (`EventBus.fromEventBusName`, `Function.fromFunctionName`, `Table.fromTableName`), never `Fn.importValue`/CloudFormation exports — cross-stack `Fn.importValue` creates a hard CloudFormation dependency that blocks the exporting stack's own updates (and defeats `--exclusively`) as soon as anything imports the export. This is why every `*.Function` project's Lambdas keep a fixed `functionName` in their CDK definition — the stable name is the whole mechanism, not an incidental detail. CI/CD is per-service GitHub Actions workflows (`.github/workflows/deploy-<service>-cdk.yml`) using OIDC, triggered on push to `development` for changes under `infra/**`, `src/Services/<X>/**`, or `src/BuildingBlocks/**`; publishes `linux-arm64` Lambda artifacts and runs `cdk deploy --require-approval never`. Add new AWS resources for a service in its `infra/constructs/*.ts` pair (mirroring the equivalent Aspire wiring in `src/AppHost/*Extensions.cs`), not just in AppHost.

## Testing

- Unit tests: xUnit + Moq + Moq.AutoMock, one project per service under `tests/Services/<Service>/<Service>.UnitTests` (plus `tests/BuildingBlocks/BuildingBlocks.UnitTests`). Tests target handlers directly, mocking repository/dependency interfaces.
- Functional tests (`Ordering.FunctionalTests`): use `DistributedApplicationTestingBuilder` to spin up the real Aspire app graph (including containers) and exercise actual endpoints after waiting for resource health. Slower; require Docker.
- End-to-end tests (`tests/E2E/`, see its README): grouped **by business context**, not by service (`tests/E2E/Checkout/Checkout.E2ETests`, `tests/E2E/Inventory/Inventory.E2ETests`, shared `E2E.Infrastructure`). xUnit + Microsoft.Playwright drive a **deployed** environment as a signed-in customer (`StorefrontSession`) or staff member of the Blazor app (`StockKeeperSession`/`SellerSession`/`AdminSession`, which also call AppSync with the app's own token) — the BFF, AppSync, the sagas and the Lambdas all run for real. `[E2EFact]` skips unless `E2E_BASE_URL`, `E2E_USER_EMAIL` and `E2E_USER_PASSWORD` are set, and `[ManagementE2EFact]` unless `E2E_MANAGEMENT_URL` and `E2E_{STOCKKEEPER,SELLER,ADMIN}_{EMAIL,PASSWORD}` are, so CI never reaches a deployed environment. The test users are dedicated `@duckstore.test` accounts whose credentials live only in `~/.config/duckstore/*.env`. Run against dev only: Checkout places real orders, and Inventory leaves deactivated `E2E-*` warehouses behind (warehouses are never deleted). UI validation goes through these suites, not ad-hoc browser driving.
- Packages/versions are centrally pinned in `Directory.Packages.props` (central package management) — add package references there, not inline versions in `.csproj` files.

## Delivering a feature from a spec and a plan

When the repo has a spec (`SPEC.md` plus per-module `SPEC-<module>.md`) and a plan (`tasks/plan.md`, `tasks/todo.md`) and the user asks for it to be implemented, act as the **orchestrator** of every phase without the mode being restated. A practice exercise is different: there Claude mentors and the user writes the code.

- **Subagents only where they pay off.** A track gets a subagent (`isolation: "worktree"`) when it is independent, substantial and worth the cold start — typically one service's slice, or a removal confined to a few services. Small or tightly coupled tasks run inline. The critical path and the shared contract files stay in the main session: `graphql/schema.graphql`, `infra/constructs/appsync-api.ts`, the SPA's `app/api/graphql/local.ts`, `BuildingBlocks.Messaging` event contracts and `MessagingSerializerContext`. At most about three tracks at once; merge them one at a time. The project agents (`cdc-integration-scaffold`, `appsync-resolver-scaffold`, `handler-test-backfill`) are for the tasks the plan points them at; `adr-guardian` runs on each phase's diff.
- **Approvals grouped, but specific.** Each approval names the action and its impact; it covers only that action, and a change of scope means asking again.
  - Dev deploys (`npx cdk deploy <Stacks> --exclusively`, `npx sst deploy --stage dev`) can be pre-approved for the named stacks. Production is never deployed from a session.
  - A deploy that has to go in order is run by Claude in that order — e.g. the SPA before `AppSyncStack` when the schema drops an argument the old SPA still sends.
  - Dropping a table or another AWS resource is asked per action, with evidence: the table is empty, and `aws cloudformation list-imports` shows no stack importing its exports.
  - AWS SSO and site logins are steps only the user can do; ask for them together, once per phase.
- **Technical checkpoints are not stopping points.** `dotnet build`, `dotnet test`, `pnpm build`/`pnpm lint`, `cdk synth`/`cdk diff`, `adr-guardian` and an approved dev deploy are run, not handed back. Stop for a failure without an obvious fix, spec ambiguity, an action no approval covers, or a step only the user can do.
- **Done matches the change.** Always: tests and build pass, `tasks/todo.md` reflects reality, and the report says what was verified. When the change calls for it:
  - this file's service description and the service README, when a service's events, tables or Lambdas change;
  - an ADR, when the decision is cross-cutting;
  - `docs/duckstore-process-flow.drawio` and its SVGs (`scripts/export-diagrams.sh`, then `scripts/validate-diagrams.py`), when the events, Lambdas or tables it draws change;
  - a dev deploy and validation, when runtime or infra changes;
  - a PR against `development`, when the work is meant to merge.
  Say in one line why each conditional item was skipped.
- **Stacked PRs.** After the base PR is merged into `development` (usually squash), and only then: fetch; confirm the merge; confirm the old base tip is an ancestor of the child branch and `git diff <old-base-tip> <merge-commit>` is empty or explained; keep local changes (`--autostash`). Then `git rebase --onto origin/development <old-base-tip> <branch>`, check the diff against `development` holds only the child's changes, and push with `--force-with-lease=<branch>:<pre-rebase-sha>`. If a check fails, stop and report.
